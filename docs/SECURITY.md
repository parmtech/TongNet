# TongNet — Threat Model & Security Research

**Not an audit.** No smart contracts, consensus proof, audited cryptography, or formal proofs have yet been supplied.

## Assets at risk

- Funds locked in pending transactions and settled wallet balances.
- Wallet private keys, one-time enrollment setup credentials, authenticator root secrets and rotating codes.
- Receiver/sender claim entitlements.
- Encrypted BlackBox contents, metadata, and distributed network state.
- Proposed operations reserve and any separate monetary backing reserve.

## Trust model and desired protections

1. **Wallet-factor compromise alone** should not allow a payment Trigger; sender BlackBox requires a distinct factor.
2. **Rotating one-minute codes are not unhackable.** TOTP can be phished, intercepted, reused within its window or generated by malware that steals its root secret.
3. **Separate-factor claim is meaningful only if keys and processing are genuinely independent.** If the wallet and Authenticator run on the same fully compromised phone, separation may fail.
4. **Cryptographic authorisation should be bound to a transaction-specific challenge** (network, transaction ID, recipient, amount, action, nonce, expiry), not just a six-digit code.
5. **Receiver-bound one-time claims** require possession of a distinct claim commitment plus verification of receiver wallet signing authority. Public keys and proofs cannot be substituted by plain address-string checks.
6. **Atomic finality** is compulsory: no network partition, replay or concurrent operation may successfully settle sender and receiver in parallel.
7. **Encryption and authenticator independence** should be built from established vetted cryptographic primitives and open, reviewed implementations, rather than inventing custom encryption.
8. **Liveness vs safety** during partitions must be specified; a decentralised system cannot assume all validators online.
9. **DoS/Sybil/spam prevention** is crucial for near-zero fees. Wallet count alone cannot grant validator influence or reserve entitlement.
10. **Private inbox delivery** must be authenticated, encrypted, address-bound, replay-safe and resilient to mailbox-node failure. Avoid any single-host dependency.
11. **Key recovery** must not silently turn the system into central account-recovery custody.
12. **Losses and errors:** wrong-address transfer, coerced Trigger, stolen device, lost factor, clock skew, malware, recovery-timeouts and chain/network reorganisation need explicit tests.

## Primary attack scenarios to test

| Attack | Required countermeasure | Status |
|---|---|---|
| Stolen wallet key initiates transfers | No Trigger possible without independent factor; locking abuse/availability impact analysed | Design only |
| Stolen 60-second access code | Phishing-resistant cryptographic challenge/signature approval; short lifetime; replay constraints | Unsolved |
| Stolen authenticator root and wallet secret | Cold recovery/freeze or strong independent emergency policy; not promised unhackable | Unsolved |
| Double sender/receiver claim | Network-wide atomic commitment/spent record and deterministic finality | Unsolved |
| Mistyped or attacker-substituted recipient address | Trigger is irrevocable by explicit user decision; wallet must highlight address and amount, provide anti-address-substitution safeguards and require transaction-bound authorisation; no guaranteed recovery if receiver claims | User rule confirmed; mitigations unsolved |
| Trigger exactly at 3-hour boundary | Monotonic consensus time and specified deadline ordering | Unsolved |
| Inbox server compromised | End-to-end encryption, independent availability, integrity checks, no server-held decryption key | Unsolved |
| Infinite fake wallets | Sybil limits independent of identities and fee economics; censorship/abuse trade-offs | Unsolved |
| Reserve fund drained or withheld | Decentralised governance, authorised protocol rules and immutable accounting | Unsolved |
| Forced reserve forfeiture | Consumer consent, legal review, ability to contest mistaken expiry | Launch blocker |

## Deployment gates

Before any real-money deployment: external cryptography and consensus audit, adversarial simulation, fuzzing and property tests, privacy and regulatory review, explicit fee disclosure, reserve governance verification, failure recovery, reproducible builds, testnet history and incident response plan.

**Critical caution:** claims that TongNet is "unhackable", "safer than Bitcoin", "guaranteed zero fee" or "the first protocol of its kind" cannot currently be substantiated.
