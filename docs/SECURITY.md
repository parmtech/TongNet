# TongNet — Threat Model & Security Research

**Not an audit.** No smart contracts, consensus proof, audited cryptography, or formal proofs have yet been supplied.

## Assets at risk

- Funds locked in pending transactions and settled wallet balances.
- Wallet private keys, one-time enrollment setup credentials, authenticator root secrets and rotating codes.
- Receiver/sender claim entitlements.
- Encrypted BlackBox contents, metadata, and distributed network state.
- Proposed operations reserve and any separate monetary backing reserve.

## Trust model and desired protections

1. **Wallet-factor compromise alone** should not allow a payment Trigger; sender BlackBox requires a distinct factor.
2. **Rotating one-minute codes are not unhackable.** TOTP can be phished, intercepted, reused within its window or generated by malware that steals its root secret.
3. **Separate-factor claim is meaningful only if keys and processing are genuinely independent.** If the wallet and Authenticator run on the same fully compromised phone, separation may fail.
4. **Cryptographic authorisation should be bound to a transaction-specific challenge** (network, transaction ID, recipient, amount, action, nonce, expiry), not just a six-digit code.
5. **Receiver-bound one-time claims** require possession of a distinct claim commitment plus verification of receiver wallet signing authority. Public keys and proofs cannot be substituted by plain address-string checks.
6. **Atomic finality** is compulsory: no network partition, replay or concurrent operation may successfully settle sender and receiver in parallel.
7. **Encryption and authenticator independence** should be built from established vetted cryptographic primitives and open, reviewed implementations, rather than inventing custom encryption.
8. **Liveness vs safety** during partitions must be specified; a decentralised system cannot assume all validators online.
9. **DoS/Sybil/spam prevention** is crucial for near-zero fees. Wallet count alone cannot grant validator influence or reserve entitlement.
10. **Private inbox delivery** must be authenticated, encrypted, address-bound, replay-safe and resilient to mailbox-node failure. Avoid any single-host dependency.
11. **Key recovery** must not silently turn the system into central account-recovery custody.
12. **Losses and errors:** wrong-address transfer, coerced Trigger, stolen device, lost factor, clock skew, malware, recovery-timeouts and chain/network reorganisation need explicit tests.

## Primary attack scenarios to test

| Attack | Required countermeasure | Status |
|---|---|---|
| Stolen wallet key initiates transfers | No Trigger possible without independent factor; locking abuse/availability impact analysed | Design only |
| Stolen 60-second access code | Phishing-resistant cryptographic challenge/signature approval; short lifetime; replay constraints | Unsolved |
| Stolen authenticator root and wallet secret | Cold recovery/freeze or strong independent emergency policy; not promised unhackable | Unsolved |
| Double sender/receiver claim | Network-wide atomic commitment/spent record and deterministic finality | Unsolved |
| Mistyped or attacker-substituted recipient address | Trigger is irrevocable by explicit user decision; wallet must highlight address and amount, provide anti-address-substitution safeguards and require transaction-bound authorisation; no guaranteed recovery if receiver claims | User rule confirmed; mitigations unsolved |
| Trigger exactly at 3-hour boundary | Monotonic consensus time and specified deadline ordering | Unsolved |
| Inbox server compromised | End-to-end encryption, independent availability, integrity checks, no server-held decryption key | Unsolved |
| Infinite fake wallets | Sybil limits independent of identities and fee economics; censorship/abuse trade-offs | Unsolved |
| Reserve fund drained or withheld | Decentralised governance, authorised protocol rules and immutable accounting | Unsolved |
| Forced reserve forfeiture | Consumer consent, legal review, ability to contest mistaken expiry | Launch blocker |

## Deployment gates

Before any real-money deployment: external cryptography and consensus audit, adversarial simulation, fuzzing and property tests, privacy and regulatory review, explicit fee disclosure, reserve governance verification, failure recovery, reproducible builds, testnet history and incident response plan.

**Critical caution:** claims that TongNet is "unhackable", "safer than Bitcoin", "guaranteed zero fee" or "the first protocol of its kind" cannot currently be substantiated.

## Disaster Recovery security decision (recorded 2026-10-24)

The creator chose an optional disaster recovery destination that is **permanently immutable** once registered. At initial registration, a distinct **one-time Disaster Recovery Key** is issued; it cannot be replaced, regenerated or reset later. Executing Run Disaster Recovery requires both source Wallet Private Key and that one-use secret, but not TongNet Authenticator/BlackBox. A valid network-level atomic recovery moves eligible funds to the preset destination, consumes the key and permanently disables the source wallet.

The key's irreversible loss disables this emergency feature, but regular transfers remain possible if the user still controls both ordinary Wallet Private Key and Authenticator Master Key. **Q5 Option A is now confirmed:** initial disaster destination registration requires Wallet Private Key proof **and** TongNet Authenticator approval. This reduces but does not eliminate attacks involving phishing, approval substitution or both factors compromised. Existing locked payments/receiver entitlements must not be cancelled or paid twice during recovery. Storing an original plaintext disaster key on a server or in GitHub would defeat its secrecy; secure commitments and independent backups need review.

The rule for wallets never activated within 72 hours is separate: they remain permanently DEAD with no reactivation. No part of these requirements has been independently implemented or audited.

## Q5 confirmation — immutable recovery destination onboarding

**2026-10-24:** User selected **Option A**: first registration requires both Wallet Private Key and TongNet Authenticator. No ability to replace recovery destination or key. Execute later using Wallet Private Key and the one-use Disaster Recovery Key, without Authenticator. In implementation, cryptographically bind Authenticator approval to the exact destination address, source wallet and nonce; a short rotating code by itself can be phished. Audit simultaneous registration attempts and finality. **Next Q6:** already locked funds and third-party receiver claims must survive disaster recovery without unauthorized cancellation or double-spend.

## Q6 — Escrow safety requirements

Disaster recovery moves available funds only. Triggered funds remain in escrow under the original receiver-first 24-hour claim window. During the subsequent 72-hour period, an existing single-use sender claim credential may be presented through the immutable pre-enrolled recovery address only after terminal disaster recovery is final. Prove transaction binding, address authority and single settlement. The recovery key does not replace a missing sender claim credential. The case of not-yet-triggered three-hour pending refunds remains open as Q7.

## Q7: Automatic timeout after disaster recovery

When the original wallet becomes permanently DEAD while an older outgoing transfer remains untriggered, its existing 3-hour lock still expires normally. Its automatic refund is delivered to the immutable registered recovery wallet. No early release is permitted. Network consensus must order the deadline and any earlier trigger or recovery operation consistently, and allow only one settlement. This is a design requirement, not an audited guarantee.

## Q8 — Disaster secret location and recovery destination acknowledgement

The user specified that the optional single-use disaster recovery secret is created in the **destination Recovery Wallet's encrypted TongNet BlackBox**, not in the original source wallet. Initial registration still needs the source wallet's private-key authorization and TongNet Authenticator approval. The later rescue action uses source Wallet Private Key plus the SAME destination-BlackBox-issued one-use disaster secret, without source BlackBox/Authenticator. At successful finalization, the key is consumed, the source's available balance is swept to its immutable destination, and the source becomes DEAD; Q6/Q7 apply to in-flight escrow.

**Q9 confirmed:** R must independently ACCEPT inside its own BlackBox before the irrevocable link is finalized or a one-time recovery secret is generated. The exact network-level cryptographic method for R's authentic acceptance is unimplemented. Such permission still does not prove S and R share a real-world human owner. Open threat cases: unsolicited association to the wrong destination, inaccessible receiver BlackBox, mailbox spoofing or withholding, replay, loss of source Authenticator before setup finality, and binding of secret commitments to exact (S,R,action,nonce). Only encrypted storage holds the secret; nodes must use proof/commitments, not plaintext. **Q9 resolved:** no key and no immutable binding until R BlackBox ACCEPT. Reject returns notice to S BlackBox; ignored request remains PENDING and NOT_CONFIGURED. Q10 pending request timeout unknown.

## Q9: Two-sided recovery pairing safety requirements (confirmed 2026-10-24)

S requests a designated recovery address with S Wallet Private Key + S Authenticator. A pending request is delivered to R's encrypted BlackBox, but **pending never means active protection**. Only verified ACCEPT from R BlackBox permits minting the one-time secret in that same BlackBox and permanently linking S to R. REJECT gives S BlackBox a failure notice with no key or link; unanswered requests remain pending with no recovery protection. To implement this, bind both authorizations to exact source/destination and unique request ID, prevent forged acceptances, duplicate acceptance/rejection races, partial link/key issuance, and inbox delivery failure. No natural person identity is proven by a cryptographic address association. Q10 confirms unanswered requests automatically EXPIRE after 24 hours, always NOT_CONFIGURED with no key/binding; prohibit stale Accept and replay. Q11 source withdrawal rules still open.

## Q10 — Pairing request expiry security

Unanswered destination BlackBox recovery-pairing requests have a confirmed 24-hour lifetime. At deadline the network must mark pending request EXPIRED and disallow later ACCEPT, key issuance or irreversible binding. Pending and expired never count as configured recovery. Authoritative deadline/time computation, accepting at boundary, forged timestamps, duplicate messages and temporary network outages all need explicit consensus and adversarial tests. This user decision does not authorise source withdrawal/replacement while still pending (Q11 open).

## Q11 — No source-side cancellation of pending disaster setup

The user confirmed Option B. Once a source wallet makes a disaster recovery pairing request, it cannot cancel, withdraw, replace or redirect that pending request. It must wait for the target BlackBox to reject or for the original 24-hour deadline to expire. Until accepted, recovery is not configured. After acceptance, the binding remains permanent. Implementation must reject parallel replacement and prevent replayed or competing requests. Q12 Option A CONFIRMED: destination Accept must be network-finalized strictly before original 24-hour expiry; a prior tap/relay receipt without finality does not qualify.

## Q12 — Strict finality timing creates outage risk

User-selected Option A requires network-finalized recovery-wallet Accept BEFORE the pairing request's original 24-hour deadline. A submission made before the deadline but confirmed afterward must be rejected as EXPIRED and MUST NOT generate the one-use recovery key or permanent pairing. The network's finality ordering and canonical clock must be attack resistant; device clocks or unverifiable relay timestamps cannot grant an exception. If validators censor or the network stalls near the deadline, legitimate requests can expire. No consensus has yet been designed or proven to secure this. **Q13** will consider separately the 24h receiver claim / following 72h sender claim timers during network-wide downtime; those have additional risks including the proposed reserve forfeiture rule.

## Q13 — Queues do not guarantee payment acceptance or protect expiring claims

User wants fixed-rate running timers despite fast/slow network, bounded queues under congestion and start of a new transaction timer only when the network accepts it. Recommend unambiguously defining network acceptance as irrevocable consensus finality, not admission to a node's local untrusted queue. Before acceptance, request may be duplicated, censored, reordered, delayed, expired or rejected. A queued state is never proof of funds transfer and cannot start a new payment timer.

Security work: queue-based denial of service, Sybil flood, malicious relay timestamping, skipped priority claims, staleness and replay, divergent queue order across validator partitions, duplicate retries, permanent backlog, no guarantees from load balancing, untrusted receipt timestamps, and finality-vs-expiry races. Bound queues and use idempotent request IDs, per-wallet fairness without enabling Sybil impersonation, separate urgent claim processing and authenticated final receipts. An existing 24h/72h claim window continues with time unless an explicit different outage policy is approved. **NO automatic promise** that a queued claim will be accepted before the deadline. The proposed forfeiture to Network Reserve on inability to finalize remains blocked for legal, consumer safety, network liveness and fairness analysis.

**Q14 confirmed Option A:** both receiver and sender financial Claim requests require network finality strictly before the applicable existing 24h/72h deadline; a queued/signed request without finality is not enough. Full-outage consequences and reserve forfeiture remain OPEN Q15.

## Q14 — Strict network finality for financial claims (confirmed)

The recipient's 24-hour Claim and sender's following 72-hour one-time reclaim must each attain consensus finality strictly before their applicable expiry. Local signing, queue admission and intermediate relay receipt do NOT stop the countdown or create a payable claim. A claim finalized late must be rejected atomically even if it had been queued early. Enforce mutually exclusive spent state across receiver Claim, sender reclaim and any later reserve disposition; protect against malicious validator ordering, backlog censorship, partition replay, stale status displays and fee/prioritization attacks. A total outage can leave legitimate users unable to settle before expiry; transferring remaining escrow to Network Reserve without additional safeguards raises severe legal, fairness and security issues. This proposal must not handle real-user forfeiture before explicit informed user consent, independent legal review, and validated liveness. Next Q15 will resolve proposed treatment after a network-wide halt, not change the previously confirmed strict Claim finality rule.

## Q15 — Universal network-latency deadline credit (confirmed requirement 2026-10-25)

The user explicitly requires a network-wide policy: all affected time-sensitive tasks (Send/Trigger, receiver Claim, sender reclaim, disaster recovery setup and other timed operations) receive **exactly the measurable attributable network-induced delay as additional time**. A 15-minute verifiable network delay entails 15 minutes added to the affected operation's effective deadline. Timers run at ordinary clock cadence and new transactions start counting only after final acceptance (Q13). Q12/Q14 strict finality still applies **before the adjusted deadline**.

Threat model: malicious nodes inflate measured latency; a user self-delays submissions by disconnecting phone; server clock lies, Sybil consensus manipulation, backpressure unfairness; attackers deliberately congest queues to extend their own eligibility; indefinite cascading extensions; duplicate interval credit across many stages; expiry/Claim/Reserve finality races. Require a decentralized verifiable delay oracle/calculator and threshold proofs, bounded exact-once interval accounting, no credit for purely local inactivity, deterministic state transitions, and alerts about adjusted deadlines. No such system is yet built or shown Byzantine secure.

Financial safety: if receiver entitlement deadline is extended, the sender's later 72h exclusivity must begin later too, and proposed irreversible reserve disposition must wait until all validly adjusted windows resolve. Q15 changes a previously assumed absolute expiry under outages; never double-claim or auto-confiscate before adjusted deadline. The proposed Reserve-forfeiture feature is NOT authorized for real assets absent jurisdiction-specific legal and informed-consent review. **NEXT Q16:** define a robust per-operation vs globally calculated delay rule and verification/anti-gaming.

## 2026-10-25 — NEWER USER-CONFIRMED RULE: Both payment Claim Keys originate in the SENDER BlackBox

**This rule explicitly SUPERSEDES older language that delivered/generated receiver Claim Key inside Receiver BlackBox or automatically delivered the key to R. It does NOT change the unrelated Disaster Recovery Key, which remains generated inside the Recovery DESTINATION's own BlackBox only on accepted recovery pairing.**

**Confirmed operation:** At transaction initiation, source Sender BlackBox generates/displays the unique **Receiver Claim Code K_R**, tied to exactly (TongNet chain, transaction ID, selected receiver address/public key, amount/asset, operation, expiry). Sender explicitly gives K_R to intended receiver by a private/out-of-band channel. The selected on-chain RECEIVER address, **not merely the person holding the code**, must independently authenticate and prove control of its wallet to claim. Sending/witnessing a code never credits funds by itself. Preserve existing separately authenticated sender BlackBox Trigger: after a successful network-final Send lock and final Trigger within the 3h window, K_R becomes exercisable for the receiver's **24h nominal** window, with Q15 verified eligible network delay adjustment. Generating K_R at Send is NOT payment settlement and its validity clock still begins on final Trigger. If no final Trigger, auto-refund after adjusted pre-trigger expiry; no receiver payout. Receiver need not create the code and network must NOT automatically supply plaintext K_R to whichever destination address Sender typed. Sender must deliver it to intended receiver.

**Next window:** At the end of receiver's adjusted 24h exclusive priority, the receiver entitlement becomes EXPIRED and **a fresh, transaction-specific Sender Reclaim Key K_S is generated in the SENDER's BlackBox**, accessible to/usable only by authenticated original Sender, never by Receiver. K_S is only valid in the following nominal **72h** (extended solely for eligible verified network delay). Sender must manually reclaim using valid K_S **plus original sender authority**, or after previously completed Disaster Recovery, the already confirmed immutable linked Recovery Wallet path IF its necessary original-claim-proof rules can be satisfied. K_S expires strictly at its adjusted expiry. No automatic full refund after 24h Triggered receiver nonclaim: rather funds become sender-claimable for next 72h. Existing user-proposed network-reserve allocation after total post-Trigger 24+72h remains legally/ethically blocked for real-money rollout.

**Wrong address failure analysis:** Sender intended wallet A, but transaction cryptographically binds to mistyped wallet B. If Sender sends K_R to A, A cannot redeem because A lacks B's wallet authority; B cannot redeem without K_R. After receiver window expires, original Sender can use K_S in the next 72h to reclaim. If B obtains K_R (through code theft, intentional sharing or phishing), B can claim before expiry. No system can guarantee refunds if both credentials satisfy the wrong recipient transaction.

**PROTOCOL ENGINEERING OPEN / conflict with earlier Q6:** Previous specification said the Sender Claim Key already existed before 24h and could be used even after Source S became DEAD by Disaster Recovery. Newly confirmed **late key generation in Sender BlackBox** conflicts with successful prior disaster recovery or lost/compromised Sender BlackBox before the 24h boundary. Do NOT silently replace the user's "new key after 24h" timing. Candidate solutions needing confirmation and formal verification include (A) Sender BlackBox generates fresh K_S after expiry while online and cannot reclaim if destroyed, OR (B) precommit an authenticated, encrypted, future sender key/derivation at Trigger, only cryptographically UNSEAL/ACTIVATE it once receiver window expires, including recovery-wallet handling. B preserves prior Q6 protection better but changes the literal issuance time. Network must not mint plaintext K_S or know secret by itself. Also prove secure commitment update at boundary, no claim if key issuance commitment missing, anti-replay, receipt binding and no permanent frozen funds.

**Naming:** Ordinary transaction keys K_R and K_S are NOT Wallet Private Keys, Authenticator/BlackBox master secrets, disaster-recovery keys, or a receiver-generated Receive Request. An extra signed Receive Request may still be a future optional defense but is NOT required/approved by this correction; do not assume mandatory upfront receiver request. The new flow is user-confirmed requirement only—not an implementation, audited code or measured performance.
