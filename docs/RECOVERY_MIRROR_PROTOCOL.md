# TongNet — Recovery Mirror Protocol (Owner clarification, 2026-10-25)
**Classification:** Latest OWNER-CONFIRMED PRODUCT REQUIREMENT + separately flagged engineering design proposals. Research/specification only, not code, testnet, full recovery or audited cryptography.
**Author / company:** ParmTech; original concept creator and developer: Manjinder Singh. Concept originated in 2015 per creator, public disclosure in 2026 per creator; history has not been independently verified.

## Latest owner instruction: continuously synchronized standby successor
When original wallet S finishes its original **immutable S→R destination pairing**, it should start keeping the exclusively reserved Recovery Wallet R's backup state **continuously synchronized** with transactions, all new BlackBox data, payment/claim records, metadata, historical receipts and outstanding conditional rights of S. R is essentially a **recovery-only mirrored copy of S's logical wallet data**, not a second spendable balance. The owner called this a "backdoor"; security engineering should treat it as a tightly restricted **cold mirror / recovery escrow**, never a unilateral signing or decryption backdoor.

Prior to Run Disaster Recovery:
- S remains the sole NORMAL_ACTIVE signer and spending authority. R stays `RECOVERY_RESERVED`, fundamentally prohibited **by protocol** from ordinary SEND, RECEIVE, CLAIM, paying fees, funds movement or authorizing a receiver claim, not simply hidden UI toggles. R is permitted only narrowly scoped metadata setup/pairing, encrypted-data backup/verification and protocol state events. Recovery setup ACCEPT remains non-financial metadata, reconciled with the user's "no transactions" requirement (no ordinary financial transactions).
- R is a fresh, never-financially-used address at first registration, and cannot receive ordinary funds while in standby even if an attacker knows its address. Consensus must reject attempts atomically, never debit a sender then burn.
- Wallet balances remain on one ledger authority/escrow system. Do **NOT mint, mirror, duplicate, move or credit** the main wallet's coins to R merely because a new BlackBox event arrives. Mirroring is **data and future successor recovery right**, not duplicate ledger spendability.
- Following accepted pairing, existing S BlackBox data should be captured in an authenticated, encrypted initial snapshot and further changes appended as versioned encrypted incremental events/checkpoints (transactions, encrypted inbox contents, one-time claim-related state, proof material, account metadata and receipts), integrity checked and available through independently accessible storage/replica nodes. Only data the source actually encrypted and backed up can be recovered; never invent missing keys or stored plaintext.
- User expects as-close-to-live synchronization as practically possible. Distributed storage, disconnected devices, concurrent event versions and outages can cause replication lag. Display backup `LAST_VERIFIED_CHECKPOINT`, sync state and stale-backup warnings; avoid claiming that a crashed/offline phone's never-synced data survives. Use independently reachable replicated encrypted storage; ensure no single ParmTech server is indispensable. Do not publish BlackBox ciphertext metadata or personally revealing content needlessly.

Upon cryptographically final `RUN_DISASTER_RECOVERY(S,R)`:
- Preserve earlier dual-authority requirement: original S Wallet Private Key **plus one-use Disaster Recovery Key** generated only within destination R's BlackBox **after R ACCEPTS pairing**. Original source Authenticator/BlackBox need not be available for invoking disaster recovery, per user rules. Any restored BlackBox content must be decrypted with material that was securely prepared before the loss, not with arbitrary control of a block explorer.
- Atomically mark S `DEAD`, R become the **SOLE NORMAL_ACTIVE SUCCESSOR**, credit only S's currently spendable/unlocked ledger balance once to R, and attach verifiable succession certificates mapping old S historical records and on-chain conditional transaction rights to R. Previously locked or pending escrow remains locked with the same receiver-first 24h then sender-next **60 DAYS** rights, without early release, double payout, or altering counterparty's rights. Which outstanding claim request and Sender BlackBox FINAL_ACCEPT may be inherited requires formal protocol rules and owner clarification. Original historical ledger does NOT move or change addresses; the successor client presents verifiable linked history.
- BlackBox restore in R should expose latest cryptographically verified backed-up snapshot and append-only events only after recovery is legitimately complete and corresponding decryption rights are available; original S BlackBox signing authority does NOT transfer simply by copying its records. Old keys must not be reused for a new spendable wallet; new R wallet keys sign as R with consensus-approved successor entitlements only.
- Prevent replay/restart race: recovery execution one-time, S and R never jointly active, no concurrent S and R spends, no rollback to S from DEAD, no replay of one-use recovery secret, no other recovery address impersonation.
- First wallet/account histories may include one-way links to R. This doesn't imply every prior caller/sender must trust R automatically; identity and successor proofs must be independently verifiable.

## Critical cryptographic tension — synchronized data vs inaccessible before recovery
Two distinct properties need not be confused:
(A) **R cannot sign/spend/claim before recovery:** enforceable as a protocol state by BFT verifying R=`RECOVERY_RESERVED`, rejecting invalid transactions even if user physically possesses its credentials.
(B) **R cannot even READ source BlackBox secrets before recovery:** storing an encrypted copy on R does not guarantee this if the decrypting key is already known to R or appears in R's software. Even if the app hides a 'view' button, a capable owner/attacker could bypass UI and decrypt the data offline. To claim confidential cold-mirror secrecy, require a designed key-release/access-control scheme (e.g., prepared split decryption shares with genuinely independent custody/hardware policy, or a cryptographically verifiable recovery-activation mechanism); threshold/shares can imply extra trust/dependency. Time-lock labels or blockchain status alone cannot stop offline decryption by a holder of the actual key. No one-provider decryption backdoor or false zero-trust promise. **Question still open:** owner prioritizes blackbox unreadability in RESERVED status versus guaranteed immediate decryption/recovery without an extra independent secret/provider.

## Additional unsolved cases
- A transaction's Receiver Claim Code K_R and Sender's new K_S: K_S is owner-confirmed as **generated after 24h in S BlackBox**. If the phone is destroyed first and recovery successor R takes over, S can't generate that key later. Simply mirroring earlier data does NOT solve it. Need pre-authorised recoverable deterministic K_S derivation or sealed future secret, with no pre-expiry claim, plus a formally audited protocol and explicit owner approval for any adjustment to literal creation timing.
- When sender S dies during a pending Receiver Claim Request, determine whether R can sign FINAL_ACCEPT as authorized successor; if yes, prohibit replay and require fresh independent human approval in R, preserve original receiver, amount and request IDs, and expiry. If not, receiver must expire and R may reclaim via properly recoverable proof.
- Initial pairing ACCEPT, reserved-wallet empty status and encrypted snapshot activation atomicity: never label backup active if no initial verified checkpoint exists. If updates lag, classify recovery data accordingly; no silent loss.
- If malicious mirror-storage or validators withhold data, authenticated version counter and receipt prove missing/stale snapshot but cannot always regenerate erased data. Need multi-replica redundancy.
- Protect encrypted backup against long-term ciphertext compromise, lifecycle key rotation, and split custody dependencies; no private key/authenticator roots sent to website server.
- Long-duration key loss, compromised backup encryption key, unauthorized lookups, 'dead wallet' activation races, multiple pairings, protocol migration, network partitions and cross-epoch BFT proof remain blockers.
- 60-day sender window then user-proposed reserve forfeiture remains unapproved for real-money use pending consumer-law/economic review and exact-delay safety proofs.

## Recommended state identifiers (candidate technical names)
`NORMAL_ACTIVE` -> (immutable recovery pairing request/accept + snapshot) `NORMAL_ACTIVE_WITH_RESERVED_MIRROR`
`RECOVERY_RESERVED` -> (verified one-time Run Disaster Recovery) `RECOVERY_ACTIVATING` -> `NORMAL_ACTIVE`
Source S at same final event -> `DEAD`.
Only the consensus-approved R may become successor. `RECOVERY_ACTIVATING` should be implemented atomically or as a nonspendable internal transitional phase, never a partial state permitting dual funds.

**Final distinction:** R is a continually synchronized encrypted BACKUP + future successor, not an ordinary second wallet with spendable funds, not a magical copy of lost keys, and not a live admin backdoor. It must remain unusable until owner-authorized disaster finality. This distinction is non-negotiable for user safety, while exact encryption/custody details are OPEN.
