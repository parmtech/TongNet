**2026-10-25.** This supplements (does NOT erase/replace) the 50 documented items in [LONG_HORIZON_RISK_AUDIT.md](LONG_HORIZON_RISK_AUDIT.md) and the [V1.1 Whitepaper](WHITEPAPER_MASTER_V1_1_SECURITY_REVIEW.md). ## Newly identified root failure modes

**L-51 [P0, RED] Original S PRIVATE KEY LOST paradox.** Current authorised `RUN_DISASTER_RECOVERY(S,R)` needs **S private signing key + R unique disaster key**. If the S *private key* is destroyed, even with fully synchronized BlackBox ciphertext, recovery CANNOT be executed. This differs from mere phone loss where backed-up private key still exists. Restoring a wallet from seed with same S identity depends on that seed surviving. **Do not call this protocol general lost-private-key recovery.** Candidate solutions require explicit owner decision: (A) maintain current design only for device loss, prominently disclose irrecoverability of root signing-key loss; (B) add a distinct S-preauthorised loss-of-signing-key capability cryptographically committed at pair time, with independent delayed confirmation/threshold guardians/timelocks and theft, coercion, griefing, 60d appeal, collusion threat models. B changes current owner security trust policy and cannot be silently adopted. Never create admin secret override. Block real-value disaster-recovery claims until exact supported loss scenarios are ratified. [#3](https://github.com/manbir6-ux/TongNet/issues/3).

**L-52 [P0, RED] ACTIVE R doesn't imply available backup or reachable R.** A recovery destination R can stay chain ACTIVE yet lose its BlackBox data, device, signer, internet access, or be malicious and withhold its one-use Disaster Key. Thus merely checking `R != DEAD` is insufficient for *usable* recovery and availability. Need periodically authenticated encrypted checkpoints with provenance, mirror lag/heartbeat transparency, redundant ciphertext nodes and safe confidentiality-preserving availability proof. A failed heartbeat must NOT make R chain DEAD or automatically reassign S recovery, because only consensus-final DEAD changes link under owner policy. Warn S of degrading assurance. [#4](https://github.com/manbir6-ux/TongNet/issues/27) [#20](https://github.com/manbir6-ux/TongNet/issues/41).

**L-53 [P0, RED] Disaster credential theft & coercion.** Original S private key plus one-use R disaster key may be obtained by colluding owners, malware or kidnapping. A thief could permanently DEAD S. Design binding to S,R,network,nonce, expiry and sender-side intent if permitted; delayed-reveal and network-visible opt-out clash with genuine immediate emergency recovery. Analyze exact owner authorization, resistance to coerced pair/accept and no unsafe admin override. [#3](https://github.com/manbir6-ux/TongNet/issues/3).

**L-54 [P0, RED] Validator consensus & recovery DEAD transaction ordering.** On S recovery, S becomes DEAD for spending immediately, but S's former validator signer may remain part of active epoch committee until quorum-safe membership change. Can't have protocol checking `source DEAD` and rejecting its validator vote midheight while the former committee is still active; consensus and payment credential namespaces must differ. Reconfiguration, slashing and successor bond withdrawal proof need formal model. [#12](https://github.com/manbir6-ux/TongNet/issues/33) [#17](https://github.com/manbir6-ux/TongNet/issues/38).

**L-55 [P0, RED] Native fee and 61-day storage-bomb.** Every LOCK can persist until receiver 24h + sender 60d plus variable delay/suspense. Flat single cheap fee with unbounded outstanding locks makes state/storage costs grow long after validators are paid. Each LOCK must prebudget verified time/state resource, cap outstanding escrow per economically scarce resources and bound payload size; reprice at safe rule boundaries without retroactively stealing already locked funds. [#18](https://github.com/manbir6-ux/TongNet/issues/39).

**L-56 [P0, RED] Genesis/first-epoch bootstrap circularity.** PoS voting needs pre-existing TONG stake, but the first issuance/genesis validators have disproportionate power before a genuinely liquid, widely-held token exists. Public 64 validator names cannot prove independent ownership, especially if founding allocations or loans relate operators. A staged **honestly disclosed temporary trust**/genesis design plus independent signing commitments, pause threshold and open distribution proof is required. Do not market starting state as Bitcoin-equivalent censorship resistance. [#9](https://github.com/manbir6-ux/TongNet/issues/34) [#10](https://github.com/manbir6-ux/TongNet/issues/34).

**L-57 [P0, RED] BlackBox release threshold itself can freeze legal recovery.** If validators/guardians hold archive decrypt shares, original authorised recovery may be BFT-final but key holders can censor release, rotate away old keys, lose shares or collude to decrypt early. Threshold geometry must be compatible with stake/epoch reconfig and disaster assumptions; shares must never be complete inside R pre-recovery. Alternate user-controlled encrypted backup is a different trust model and must be described honestly. [#4](https://github.com/manbir6-ux/TongNet/issues/27).

**L-58 [P1, AMBER] 3-stage transaction lifecycle is not universal instant-pay.** Bitcoin-like users may expect immediate straightforward transfers, but owner confirmed mandatory manual Sender FINAL_ACCEPT. Request/approval can be held, offline or malicious; receiver cannot treat LOCK or code as payment. Design explicit wallet UX and SLA warnings rather than silently adding unapproved one-step mode. [#19](https://github.com/manbir6-ux/TongNet/issues/40).

**L-59 [P1, AMBER] Validator economics can bankrupt small honest nodes.** 64 consensus nodes, 32 standbys, 128 full nodes and 16 archives have continuous costs. Low fees plus low utilization may not cover electricity/cloud/ops, while treasury emissions dilute users and make early distribution critical. Measure 5-region operational cost, low-use baseline and long-run chain state storage before guaranteeing Fee + Earn. [#10](https://github.com/manbir6-ux/TongNet/issues/34) [#18](https://github.com/manbir6-ux/TongNet/issues/39).

**L-60 [P1, AMBER] Pending 61-day transactions across protocol upgrades.** New signature formats/deadline rules must not erase or reprice in-flight escrows. Always version signed claims, BlackBox key proofs, fee reserve, slashing bonds and planned recovery event; keep old transition verifier until every old live escrow expiry/recovery right safely resolved or ratified migration. [#15](https://github.com/manbir6-ux/TongNet/issues/30).

**L-61 [P1, AMBER] Data deletion/privacy and sealed cross-parent archive in R→C.** Encryption and ciphertext copies copied onward via a separate R archive do not automatically erase after S→R link revocation. A DEAD R's own recovery C cannot read S archive; proof of cryptographic erasure and practical retention policy separate from immutable chain history and privacy law. [#20](https://github.com/manbir6-ux/TongNet/issues/41).

**L-62 [P1, AMBER] Light clients and validator trust after months offline.** PoS weak-subjectivity trust periods and set upgrades mean a long-offline phone cannot safely trust arbitrarily old endpoint/committee signatures. Define recent trusted checkpoint update, quorum certificate verification, hostile eclipse protection and safe warning. [#16](https://github.com/manbir6-ux/TongNet/issues/37).

**L-63 [P1, AMBER] Independent wallet and validator key rotation lifecycle.** Rotation must not reuse signatures, leak bonds, disable legal recovery, reopen old escrows or permit replay after a permanent DEAD status. Define key epoch binding, downgrade protection, revoked-key proof and hardware-backed storage/backup alternatives. [#19](https://github.com/manbir6-ux/TongNet/issues/40).

**L-64 [P1, AMBER] Open-source supply chain & AI worker compromise.** Malicious CI dependencies, malicious automated PR, GitHub token leaking, unpinned workflows and compromised validator updates can break cryptography despite sound whitepaper. Require branch protection/review, least privilege tokens, SHA-pinned third-party actions, reproducible signed release and SBOM; bot should never merge fund logic by itself. [#22](https://github.com/manbir6-ux/TongNet/issues/46) [#23](https://github.com/manbir6-ux/TongNet/issues/24).

**L-65 [P1, AMBER] Multiple tracking systems cause stale contradictory status.** Older docs referenced `docs/PROJECT_STATUS.md` and free-form TN-AREA-* issues whereas newly created live issues use TN-001..TN-023. Resolution: [AGENTS.md](../AGENTS.md) unifies GitHub Issue OPEN/CLOSED as canonical task truth; tracking manual handoff/journal and bot-derived snapshots are derivative; no two independently authoritative status boards. [#23](https://github.com/manbir6-ux/TongNet/issues/24).

## End-to-end regression matrix additions

- Device lost but original S signing key backed up; device lost and S signing key *never* backed up; key stolen but intact; Authenticator lost while BlackBox intact; R ACTIVE but refusing cooperation; R on-chain DEAD during pending disaster; R offline without network DEAD; R→C recovery before S→R; K_S never issued and Sender DEAD; Sender recovery while it is consensus validator; network partition/timeout + wrongful forfeiture; fee spam with escrow storage.
- In every case test fund conservation, irreversible S DEAD safety, no early parent BlackBox decryption, 24h receiver priority followed by 60d sender priority, no automatic S→C redirect, inability of validator to forge S BlackBox ACCEPT, and honest statement when recovery mathematically impossible.
- At 3/6/12/24 months repeat economic attack-cost, weak-subjectivity, library CVEs, staking concentration, cloud operator correlation, seed/rpc independence, data archive restore and emergency key compromise drills.
