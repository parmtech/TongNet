# TongNet — 2026-10-25 owner decisions: trusted bilateral P2P, 60-day reclaim, reserved recovery successor

**Status:** OWNER PRODUCT REQUIREMENTS + ENGINEERING PROPOSALS SEPARATED. Not coded, tested, audited, or approved for custody/real money. **Latest requirements supersede 72-hour sender reclaim** in older records. Manual Sender BlackBox FINAL_ACCEPT (no 3h Trigger) remains latest protocol direction.

## 1. Product scope — owner confirmed
TongNet is an **unmediated, trusted-party bilateral P2P payment rail**, not a seller/buyer dispute resolution, escrow arbitrator or compulsory merchant-fair-exchange platform. Sender and Receiver conduct real-world dealings independently via WhatsApp, voice calls etc; each party chooses a counterparty they trust. Sender's final BlackBox ACCEPT is mandatory before Receiver settlement, otherwise receiver cannot receive the money. There is **NO THIRD PARTY DEAL ARBITRATOR** with override keys or compulsory unilateral reversal. The independent BFT validator network is still a *cryptographic transaction-ordering/finality service*, not a mediator resolving whether external goods or services were delivered. A dishonest sender can withhold ACCEPT after receiving goods. Present that risk and require network finality before treating a transaction as paid. No absolute protection from phishing or compromised signers.

## 2. Claim/reclaim — owner confirmed
After a network-final locked initiation of an ordinary manual P2P transaction, the **receiver has an exclusive 24h nominal window** to submit its claim with Sender-generated out-of-band K_R and exact receiver wallet signature, and Sender must FINAL_ACCEPT that exact request. If NOT final by adjusted receiver deadline, K_R expires. Then original Sender has **60 full days** (replacing the older 72 hours) as an exclusive MANUAL reclaim window, using appropriate cryptographic authority and a sender claim secret K_S. Sender rights become available at the end of Receiver priority, not an automatic balance refund at 24h. A successful receiver or sender claim consumes that single escrow value once. Existing user-confirmed verifiable network-attributable delay extensions must not overlap/double count; exact provability remains unresolved. **Proposed 24h clock anchor at BFT-final LOCK** after removing old 3h Trigger is NOT expressly ratified yet. Nominal total window is 24h + next 60 days = **61 days** from that proposed anchor.

After the adjusted 60-day reclaim deadline, if still unclaimed, the user wants remaining escrow to move **automatically to the TongNet Network Reserve** to fund network costs. **Record as owner-confirmed design intent, NOT real-money deployment permission**. Permanent user forfeiture presents serious consent, legal, network outage and malicious delay-gating risks; no mainnet implementation until reviewed and tested. Define how to avoid both never-ending escrow and irreversible unsafe confiscation, with any source-ownership rights changes explicitly owner-ratified.

## 3. Reserved successor Recovery Address — owner confirmed
- Special Recovery Wallet *type/status* distinct from NORMAL_ACTIVE and DEAD, with a brand-new address. At reservation/registration it must have **zero historical ordinary financial transactions** and remain incapable of ordinary SEND, RECEIVE or CLAIM while RESERVED. The only permissible setup communications are authenticated metadata/protocol pairing ACCEPT/REJECT and crypto verification, **not user-fund transfers**. This reconciles the fact that registering and accepting an on-chain association itself may technically be a ledger operation; "first transaction must be Recovery" means **first FINANCIAL transaction**.
- Source S initiates immutable S -> R recovery pairing with Wallet Private Key + TongNet Authenticator. Reserved R's own BlackBox explicitly ACCEPTS before irrevocable attachment and one-time Disaster Recovery Key creation **inside R BlackBox**, as previously confirmed; setup ACCEPT still finalises before its 24h pairing cutoff (plus eligible verified network delay adjustment). Mere request PENDING is NOT CONFIGURED. Reserved R may not be bound to multiple unrelated source wallets under an engineering recommendation that needs formal validation/approval.
- R remains recovery-only and no ordinary incoming/outgoing transfer can target R until an actual verified **RUN_DISASTER_RECOVERY(S,R)** transaction occurs. Validate a state machine rather than only UI block. The exact rule for an attempted deposit to R must be atomic REJECT (no user fund debit, no burn).
- Once legal original S recovery consent (S Wallet Private Key + one-time immutable Disaster Recovery Key, as previous) is network-finalised, R becomes successor wallet (proposed statuses `RECOVERY_RESERVED` -> `RECOVERY_ACTIVATING` -> `NORMAL_ACTIVE`), S becomes permanently DEAD. Sweep only S **spendable** balance atomically (not outstanding conditional escrow owned by counterparties), and migrate the legal authority for S-related pending claimant/accept/reclaim obligations to R through an authenticated, protocol-visible S->R successor certificate; pending receiver rights must not be shortened or duplicated.
- User wants a full **BlackBox 'carbon copy'** (inbox, history, metadata, claim credentials and pending operations) and prior wallet history available in the successor; do NOT claim immutable historical ledger transactions can physically be moved or have their original sender/recipient address rewritten. Old ledger stays immutable; new R client presents verifiable history with source-to-successor link and event provenance.
- If owner loses phone + local wallet + BlackBox, normal restore on fresh device or trusted official web wallet should work with surviving Wallet Private Key and Authenticator Master Key **only if a recoverable, authenticated, encrypted BlackBox backup and appropriate decrypt/derivation materials were already arranged**. Network cannot conjure lost secret or plaintext from old device absence.
- Website security: never enter Wallet Private Key or Authenticator Master Key into a server-side login form or transmit them to any website backend. Only authenticated local-client signature challenges and on-device encryption/decryption are acceptable; WebAssembly/client-side crypto may be studied with realistic browser compromise/phishing risks. Owner-supplied root secrets should ideally remain offline / hardware protected and be used only via robust local recovery software.
- **Design proposal, not yet proven or separately approved:** create an encrypted, integrity-authenticated versioned BlackBox backup from initial setup, re-encrypted under a recovery-data encryption scheme accessible with previously prepared R recovery secrets; replicate to independent nodes/user-designated storage. Never assume R can generate missing plaintext or sign as the original Wallet S. R obtains only permitted successor authority after authenticated recovery finality; new fresh signing credentials for R required.
- Distinguish restoration of lost *device* while S remains ACTIVE (same wallet/account restored locally) from **Disaster Recovery** that permanently kills S and activates R.
- Sender's newly created reclaim key K_S after Receiver 24h is **still a protocol blocker** if S BlackBox destroyed/DEAD before issuance: a recoverable commitment or independently recoverable generation mechanism is needed. Future key pre-generation/sealed activation would change the literal 'generated only after 24h' rule and thus needs owner approval. Do not fabricate K_S centrally.
- The treatment of **pending sender FINAL_ACCEPT requests/escrow when S becomes DEAD** and R succeeds S requires exact, auditable authority delegation. Existing Q6/Q7 old 3-hour Trigger rules are obsolete. No hidden admin permission to reauthorise a different beneficiary or confiscate funds; formal verification required.

## 2026-10-25 — OWNER-CONFIRMED: Recovery successor can later register ITS OWN future recovery

**Latest exact lifecycle, replacing any interpretation that a Recovery Address is permanently recovery-only:**

1. While main wallet S is `NORMAL_ACTIVE`, its pre-accepted designated R stays `RECOVERY_RESERVED`. R is **exclusively a future successor**: no ordinary SEND / RECEIVE / CLAIM, no second recovery wallet associated *to R*, no `RUN_DISASTER_RECOVERY` initiated *from R*, no funds spending, nor any alternate activation. R can ACCEPT pairing protocol metadata, host continuously synchronized encrypted BlackBox mirror backups, and receive authenticated status/checkpoint events, but these are **not normal financial transactions**. The original S may have one immutable active S→R relationship as already confirmed.
2. `RUN_DISASTER_RECOVERY(S,R)` with the previously confirmed original S Wallet Private Key + one-time Recovery Key from R BlackBox, and previously accepted immutable binding, must have BFT finality and atomic state update: S `DEAD` (forever), R `NORMAL_ACTIVE` (ordinary financial controls restored) and exactly-once transfer of **only eligible unlocked S funds**. All pending locked escrow obligations and rights survive as successor-authorised entitlements without double spend or arbitrary retroactive finalisation; BlackBox mirror copy is unlocked/restored according to separately audited encryption/backups, and historic S transactions remain unchanged on ledger but linked to R for view/proofs.
3. **Only AFTER R is `NORMAL_ACTIVE` may it optionally request and pair a BRAND-NEW, NEVER-FINANCIALLY-USED successor address C as `RECOVERY_RESERVED`** using the normal recovery association protocol (R Wallet Private Key + R's separate Authenticator, C BlackBox explicit ACCEPT, no key/link before Accept). The old S→R permanently consumed/successful recovery record stays immutable. R may now spend/send/receive like any main Wallet, and C remains unusable for ordinary actions until `RUN_DISASTER_RECOVERY(R,C)` makes R `DEAD`, C `NORMAL_ACTIVE`. This may recur (S→R→C→D...). A reserved R may **never** preconfigure C in advance of its own activation.
4. Never treat S/R as simultaneously ACTIVE or as cloned funds. The state machine must reject transitions, loops, recycled/used successor addresses, multiple reserved successor registrations that conflict, claims by R while reserved, old S signatures post-death, and chained recovery before predecessor is dead. Domain-separate every source+destination+epoch transition and consume one-use recovery secret atomically.
5. The term "same wallet" means a logically continuous user history and entitlement, **not identical private keys, not a shared live signing authority, not a ledger rewrite, nor a universal decryption backdoor**. Source S private key never becomes R's wallet private key.
6. What happens to original locked sends and late-created Sender K_S when S dies, plus strong pre-activation confidentiality of R's encrypted mirror, remain critical engineering OPEN. Never quietly claim those are solved by replication.

**Decision status:** 1-3 are explicit owner-confirmed UX/protocol direction. 4-6 are safety interpretation and unresolved engineering constraints. No running chain or audited cryptographic key migration exists.
