# TongNet — Future-Proof Architecture Review and Candidate Technical Baseline
**Review date:** 2026-10-25 (Australia/Sydney)  
**Status:** DESIGN RECOMMENDATION / RESEARCH; not a launched, coded, proven or audited blockchain.  
**Authority:** Preserve *user-confirmed* payment, wallet and recovery requirements. Proposed changes are NOT retroactively user-confirmed; mark explicit consent and real-money launch blockers.

## North star and feasibility
TongNet should aim to minimise *single-party trust and vendor-dependent runtime infrastructure*, rather than promising physical zero dependencies. Decentralised computation still relies on hardware, internet links, software libraries, cryptographic assumptions, economic incentives and independent operators. No permissionless secure voting mechanism can be assumed simply because nodes have different keys; Sybil resistance needs a hard-to-fake scarce resource / independently verifiable eligibility / economic identity, and each approach has drawbacks.

Design goals: safety before liveness; genuinely independently verifiable finality; self-custody, strong compartmentalised wallet keys; very low user-facing fee, with fee-sponsored quotas if economically viable; objective performance benchmarks; no unaudited custom cryptographic primitives; graceful partition and outage degradation; protocol evolution with versioned state transitions; long-lived cryptographic agility. Do NOT claim "100% decentralised", "unhackable", "guaranteed fee-free", "world-first" or superior TPS before evidence.

**Originality:** Distinctive combination of (i) two-phase irreversible Send/Trigger, (ii) recipient 24h + sender following 72h one-use right chain, (iii) protected encrypted BlackBox, (iv) independently approved immutable disaster recovery, (v) verifiable one-to-one deadline delay compensation, (vi) adaptive protected-mode safeguards, and (vii) evidence-based automated validator governance is a candidate TongNet product architecture; novelty and freedom-to-operate are NOT proven. Reusing audited standard building blocks is security best practice, not copying proprietary code. Check each component's licence and undertake prior-art / trademark / patent review.

## Chosen primary implementation language — Rust (owner-delegated 2026-10-25)

The owner asked the assistant to select the best language. **Decision: Rust is TongNet's primary production language** for consensus, P2P node, cryptographic transactions, deterministic execution, wallet and disaster-recovery shared logic, BlackBox encryption, delay-proof state machine, validator lifecycle and light-client verification. The justification is native performance without a GC dependency, memory-safety checks by default, strong concurrency abstractions and broad cross-platform library support. This is a relative engineering tradeoff, not a guarantee of defect-free code or latency. C and C++ are not primary choices due to their extra memory-unsafe development burden; well-audited C code via narrow FFI may be acceptable if necessary.

**Engineering requirements:** minimise `unsafe`, deny unsafe code by default in money/state modules unless specifically security-reviewed; use peer-reviewed libraries, a pinned Rust toolchain and audited dependency/SBOM licence policies. Use differential/property-based testing, state-machine fuzzing, mutation tests and independent code audits. Consider idiomatic tokio-style asynchronous networking with backpressure; benchmark against simpler alternatives rather than assume best performance. Expose a versioned C ABI or a maintained Rust foreign-function binding layer where necessary. Android UI may use Kotlin, iOS UI Swift, desktop UI Tauri/native frameworks after UX and resource evaluation, keeping all transaction authority in the shared Rust engine.

**Deployment caveat:** no chain/source code has been created by choosing a language, and software still relies on libraries, hardware and networking. '100% written in Rust' across all external libraries and UIs is not a requirement; zero *single vendor/cloud runtime settlement dependency* is the goal.

## Consensus fabric: design choice
**Working name:** TongNet Quorum Fabric (TQF), *not* a claim of a newly proven consensus algorithm. Begin with a well-reviewed deterministic-finality BFT engine with explicit committee reconfiguration safety (e.g. evaluate CometBFT / HotStuff-family implementations under licences and technical suitability). Model validators as 3f+1 *effective independent fault domains* when equal vote weight is proven appropriate; generally require >2/3 of **eligible voting power**, not merely "2/3 of names". Safety assumes Byzantine fraction below threshold and quorum-intersecting epoch changes; a 60/40 split without quorum must HALT finality on both sides. 67% is not itself proof of honest operators. Quarantine/suspension cannot retroactively invalidate a signed final block.

**Performance pipeline:** (1) redundant P2P ingress/gossip and bounded, anti-spam queues; (2) parallel cryptographic prevalidation and dissemination; (3) consensus ordering and signed finality certificates; (4) deterministic execution with parallelism only for proven non-conflicting state; (5) verifiable state proofs and archival witnesses. Evaluate DAG dissemination / uncertified DAG fast consensus **only after** differential testing, formal proofs of integration and security review. Do NOT transplant Mysticeti, Narwhal or another algorithm without respecting licences/assumptions. Start simple and correct, add fast path behind opt-in testnet feature gates.

**Transactions:** domain-separated signatures for chain ID, version, transaction ID, operation type, source/destination, value, expiry and nonce; atomic state transitions; one-use claim secrets; encrypted BlackBox messages with independent off-chain delivery (contents never a consensus dependency), on-chain commitment and retry; light clients can verify finality from multiple untrusted peers.

## Validator admission, automated governance and protocol evolution
**Q19–Q25 user confirmed:** C anti-Sybil decentralised committees; C hybrid evolution from verified launch validators toward open validation; C fully automated addition/removal via pre-set rules; B quarantine and objective investigation with restoration or proven removal; B standby validator eligibility and automatic replacements when safe; C cryptographic quorum on network partition; B ONLY pre-authorised backup rotation with quorum-intersection-preserving rules during partitions.

**Important reconciliation:** "initial independently verified validators" plus "no owner/admin approval" needs verifiable *on-chain qualification* administered by a publicly specified rule set, not private discretionary gatekeeping. In phase 1 independent operator attestations have residual trust; openly disclose and measure it. No fake-node immunity simply from KYC, hardware, stake, AI, reputation, committee rotation or signature checking. **Recommended hybrid anti-Sybil eligibility:** modest slashable performance/security bond (a PoS *component*, not pure wealth-weighted PoS), multi-source proofs of durable independent operation, transparent epoch-based enrollment and public eligibility/exit certificates. Cap voting influence **only where a unique operator/control cluster is actually provable**, not per freely creatable account. Bond alone does not prevent a wealthy attacker accumulating majority, nor does identity solve worldwide permissionless access. Periodically reassess decentralisation and concentration, with staged permissionless enrollment gated on tested threat assumptions.

**Automated governance rules:** public state machine, authenticated fraud evidence (e.g. provable double-sign), time-bounded quarantine when protocol-defined objective triggers are met, automated appeal/restoration based on evidence, cooldowns and independent reason codes. High-priority emergency patch cannot grant arbitrary fund-moving administrator keys. Evidence-based removal should not conflate a node being offline with fraud. Reserve governance and upgrades must require safe networkwide on-chain change control with time-lock and broad stakeholder review; precise threshold/electorate needs formal specification. Queue/reconfiguration windows must avoid deadlock: in an actual 60/40 partition, two halves must NEVER each independently promote enough standbys to claim a separate quorum. Precommitted backups only if membership-change quorum intersection is proven; otherwise fail closed.

## Universal Network Delay Calculator (Q15–Q18)
User-confirmed: ALL affected time-bound operations receive verified network-caused delay **one-to-one** as a deadline credit; use **Hybrid** individual receipt/processing proof + network-wide health (Q16 C), independent cross-checks against fabricated individual delay (Q17 C), and cryptographic consensus on evidence or protected suspense when disputed (Q18 C). The physical timer is not slowed. Finality must occur strictly before the **adjusted** deadline (Q12/Q14). These rules apply to Send/Trigger 3h, receiver Claim 24h, sender reclaim following 72h, recovery pairing Accept 24h and other time-bound functions. A newly created request gets its timer ONLY after canonical network acceptance; pre-acceptance queue time cannot also be counted as post-start delay credit.

**Candidate calculator specification; not yet proven:**
- Collect privacy-minimised signed, bounded admission/processing receipts from *multiple independently eligible* relays and consensus epoch/height information, plus independently signed global liveness observations. A single relay's clock or a user's phone is not trustworthy.
- Build verifiable *eligible network-caused time intervals* for a given operation. Use set-union of overlapping intervals, not individual delay + global delay as arithmetic sum. Credit each qualifying second once against its applicable deadline; do not credit time attributable solely to deliberate late user submission, offline devices or pre-timer waiting.
- Represent deadlines as deterministic state/canonical consensus-time operations, with a bounded clock-skew assumption stated in the threat model; **cannot objectively distinguish all network faults from censorship in a fully asynchronous network**. Where evidence is insufficient, funds/actions transition to a narrowly-scoped PROTECTED_SUSPENSE state, not to an irreversible conflicting spend/refund/reserve. How to eventually exit protected mode without central discretion is a hard unsolved protocol and liveness risk.
- Receiver's compensated priority must end BEFORE sender-only 72h starts; do not open simultaneous rights. Auto-refund after 3h must not preempt a qualifying Trigger; disaster registration must not be marked EXPIRED if a legitimate adjusted Accept is still possible.
- Finalised transactions must not be revoked by an after-the-fact slowdown certificate; design escrow settlement barriers and epoch-final evidence watermarks before expiry. Otherwise an attack could retroactively alter rights.
- All committee evidence is accountable and public-auditable without leaking user private keys, exact payment metadata beyond necessary exposure, or BlackBox contents. Test manufactured congestion, partitioned receipt censorship, timestamp manipulation, continuous outages, and unbounded locked-fund backlog.

**Unresolved technical proof obligation:** there is no perfect global oracle for "how many seconds the network caused delay" under arbitrary partitions. Q15's policy is a goal with fundamental availability/synchrony limits; protect funds rather than pretend a mathematically exact universally objective answer exists in every case.

## Fees, economics, token and funding
Network resources always have costs. **User experience goal:** zero-visible-fee payments within a sustainably funded fair-use quota, with transparent fractional fees or sponsored transactions for others. Validator incentives may draw on legitimately funded protocol revenue, subscriptions/sponsor pools, merchant services or transparent emissions, if reviewed. Unlimited unconditional zero-cost transactions would invite spam and insolvency. Use bounded ingress admission, per-resource budgeting, anti-Sybil quotas and a transparent congestion price for non-sponsored excess. Don't hide fees in spread, inflation or unannounced locked balance.

Do NOT conflate TongNet Network Reserve (operating cost fund) with proof of currency backing. Recommend initially a clearly defined non-redeemable utility token only *if* legitimate network demand exists; define capped or fully predetermined auditable issuance/emissions BEFORE minting. Stable 1:1 fiat redemption would introduce custody, trusted collateral, and strong regulatory obligations; don't promise without licensed structure. No claim about price appreciation.

**Material override proposal needing explicit user acceptance:** previous user-stated automatic forfeiture of all unclaimed Triggered escrow after recipient 24h plus sender 72h is dangerous, and especially catastrophic under network delay/outage. RECOMMEND stop irreversible confiscation; keep a reclaimable protected entitlement or pre-agreed sender refund following additional safety policy, and fund network through voluntary opt-in donations/sponsorship rather than forced forfeiture. This is NOT a user-confirmed replacement. Until legal, economic and consumer review, the old reserve-forfeiture rule is a HARD real-money launch blocker and must remain disabled.

## Wallet, keys, Authenticator, BlackBox and disaster recovery
Maintain user-confirmed product rules in DECISIONS/PROTOCOL: initial Authenticator activation no later than 72h or wallet DEAD; 60-sec Authenticator code; irreversible Send lock, 3h Trigger or refund; 24h receiver claim then sender 72h one-use reclaim; no post-Trigger sender cancellation; original disaster recovery dual approval and immutable R pairing; one-time disaster key created **only in R BlackBox upon R's accepted and network-finalised pairing**, recovery needs original source private key + that key, DEAD source, immediate unlocked-only sweep, outstanding triggered and untriggered escrow obey distinct original rights, adjusted when network-caused delays are verified. No user support backdoor and no reversible DEAD state.

**Security upgrades, not replacement decisions:** device hardware-backed key store where available; trusted transaction display showing full destination and amount, clipboard attack mitigation; standard audited end-to-end message encryption with authenticated recovery and encrypted replicated BlackBox message storage; no plaintext server recovery of secrets; one-time secret hashes/nullifiers on chain, not raw one-use secrets; Authenticator enrollment rate limiting and replay protections; no TOTP as sole transaction authorisation—explicit transaction-bound signatures and hardware confirmation; optional externally backed-up seed only with user-approved wallet recovery design (does not override immutable disaster setup). Security warnings and small default exposure limits for unaudited irreversible 72h activation and immutable lost-key rules. Do not promise all device malware can be defeated.

## Scale, privacy, upgradeability, future proof
Keep cryptographic algorithms, signature envelope version, account state commitment and wire protocol upgradeable through protocol-consensus governance with migration periods and reproducible builds. Study post-quantum **ML-KEM/ML-DSA** per NIST as a planned hybrid migration, not an unsupported claim that Q-safe cryptography already protects the chain. Encrypted BlackBox contents should never reveal key material to validators. On-chain amounts/addresses remain linkable unless special privacy proofs are implemented; selective disclosure and confidential amounts need separate audited protocols, not wishful thinking.

Parallel execution for nonconflicting account operations; later proof-carrying sharding/parallel lanes only after a globally serializable asset owner/spent-nullifier model prevents cross-shard double spends. Archive nodes and succinct/verifiable state snapshots reduce storage burden. No privileged single API, CDN, NTP, DNS, cloud, mobile push, app store or foundation must be required for base settlement; multiple community-operated transports/bootstrap mechanisms and offline sync paths are needed. Real-world connectivity/power dependencies remain unavoidable.

## Trial targets (aspirations, not achievements)
Propose measured **median <2s and P95 <5s finality** for simple payment on a realistic geographically dispersed *healthy* testnet at **>=1,000 sustained transfers/sec** as initial aspirational performance gates, not guaranteed commitments; define percentile windows and allowed failure budget. Compare proof-verified finality with other systems on identical test harness and payload, and measure tail latency, validator counts, bandwidth, disk, CPU, power, throughput under malicious faults, recovery duration and total cost per successful transaction. Do NOT select DAG/fast-path solely from published peak TPS (lab results vary).

## Sequenced gates
1. **Threat model and formal core state machine** incl. clocks, double-spend safety, escrow and immutable wallet rights; economic/legal/IP feasibility.
2. **Single-node deterministic simulator** with property tests, differential implementation and exhaustive edge-case fuzzing.
3. **Multi-node testnet** with explicit fixed-membership BFT, secure committee transitions, escrow state proofs and fault injection; automated rules demonstrably non-bypassable.
4. **Adversarial public testnet** with bounded eligibility, measured latency/throughput, sponsored-fee sustainability, BlackBox/recovery E2E checks, recovery from partitions and no silent fund loss.
5. **Independent cryptography, consensus, smart-contract, wallet, economic, privacy, regulatory and reproducible build reviews; funded incident-response plan**.
6. **Staged mainnet** ONLY when hard blockers cleared; publish decentralisation concentration metrics and version upgrade policy; allow progressively more open validators only with evidence, not calendar dates.

## Immediate launch blockers (do not paper over)
- Robust Sybil-resistant automated validator eligibility and safe membership reconfiguration with no arbitrary privileged owner.
- Consensus implementation, proof of quorum intersection and double-spend invariants across partitions.
- Mechanically auditable delay-credit proof in partial outages and resolution of PROTECTED_SUSPENSE, with a hard guarantee against reserve/conflicting rights race.
- Initial activation DEAD rule and permanently immutable recovery key/user-harm assessment.
- No unapproved confiscation of unclaimed funds; informed user consent, Australian and other jurisdiction legal review.
- Token issuance, wallet/app security, economic sustainability of sponsored/microfee transactions, vulnerability disclosure/patch governance.
- Benchmark evidence, independent external audits and operational rollout/rollback plans.

## Consumer payments, trust and regulated-finance critique (2026-10-25)

**Critical architecture challenge:** the legacy confirmed Send -> separate Trigger -> 24h receiver Claim -> subsequent 72h reclaim is NOT competitive for routine retail checkout if it is the ONLY payment type. Propose alongside it a strictly separate `Instant Pay` atomic direct-payment variant with one clear cryptographically transaction-bound approval and network finality; keep existing old path unchanged as `Protected Pay`. The dual-mode addition is a **new, unratified design recommendation**; do not smuggle a change to the original confirmed contract rights. Both modes require consistent anti-spam fees, state proofs and fraud/irreversibility disclosures.

Competitor comparisons: Solana offers fast/sub-cent fee payment and fee abstraction; Stellar is already a low-cost cross-border payment rail; Sui supplies convenient onboarding; Ethereum L2s provide ecosystem/low-fee infrastructure. TongNet must earn adoption through verifiable user-controlled security and risk-specific payment choice, merchant receipts/SDK, sustainable price and a legal fiat integration path—not unsupported first-ever/performance rhetoric. Banking functions require separately licensed partners or appropriate authorisations. Candidate supply **1,000,000,000 maximum TONG with 9 decimals** is an illustrative unit-economics placeholder only; no cap, vesting, allocation or release is chosen, and money supply doesn't itself establish market worth.
